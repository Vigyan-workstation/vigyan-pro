# Requirements Document

## Introduction

Vigyan Pro v5.0.8 Free Tier is the first publicly stable release of Vigyan Pro Workstation — a 100 % offline STEM desktop application built with Svelte 5, Tauri, and a Python/llama.cpp backend. The release addresses three critical bugs found in v5.0.7 (false CAS badges, chat scroll failure, raw token leakage), replaces the model fleet with three Apache 2.0 sovereign models, wires the existing derivation receipt system end-to-end, redesigns the UI shell with a distinctive ExperimentLab identity, and adds `vigyan verify` and `vigyan receipts` CLI commands. The tier is free for personal, academic, and non-commercial research use with no license key, no account, and no cloud dependency.

---

## Glossary

- **App**: The Vigyan Pro desktop application (Svelte 5 + Tauri v2).
- **Backend**: The Python process (`launch_desktop.py`) that manages llama.cpp inference, the SymPy CAS engine, and the SSE event stream.
- **CAS**: Computer Algebra System — SymPy 1.14, used for exact symbolic mathematics.
- **Chat_View**: The main conversational panel rendered by `Chat.svelte`.
- **CLI**: The `vigyan` command-line interface implemented in `vigyan_cli.py`.
- **Coral_Accent**: The hex color `#FF7B5F` used as the primary interactive accent throughout the UI.
- **Daily_Model**: Gemma 4 E4B — `gemma-4-e4b-qat-q4-0.gguf`, 2.5 GB, 5 GB RAM, 128 K context.
- **Production_Model**: Vigyan-7B Quad-Master — `vigyan-7b-quad-master-q4_k_m.gguf`, 4.16 GB, 8 GB RAM.
- **Advanced_Model**: Gemma 4 12B — `gemma-4-12b-qat-q4-0.gguf`, 6.7 GB, 13.4 GB RAM, 256 K context.
- **Model_Switcher**: The 3-segment nav control in the titlebar for selecting among Daily, Production, and Advanced models.
- **Receipt**: A `.rcpt.json` file conforming to the Vigyan Receipt Schema v1.0, generated by `derivation_receipt.py` for each CAS-verified computation.
- **Receipt_Inspector**: The right-panel Svelte component (`ReceiptInspector.svelte`) that displays receipt fields and audit actions.
- **Receipt_Badge**: The inline per-message badge that shows one of three verification states: Verified, Unverified, or Unable_to_Check.
- **Session_Rail**: The 220 px left sidebar listing past chat sessions.
- **SSE**: Server-Sent Events — the event stream from the Backend to the App frontend over the local HTTP bridge.
- **SymPy_Engine**: The SymPy 1.14 CAS instance running inside the Backend.
- **Titlebar**: The 36 px top bar containing traffic-light controls, app title, Model_Switcher, and status indicator.
- **Command_Palette**: The ⌘K modal overlay for keyboard-driven navigation.
- **Free_Tier**: The non-commercial license tier — free for personal, academic, and research use with no account required.
- **Receipt_Store**: The directory `~/.vigyan/receipts/` where Receipt JSON files are persisted.

## Requirements

### Requirement 1: Fix False CAS Verification Badge

**User Story:** As a student using Vigyan Pro to solve calculus problems, I want the "CAS Verified" badge to reflect whether SymPy actually checked the answer, so that I do not mistake an unverified LLM response for a proven result.

#### Acceptance Criteria

1. WHEN the Backend returns a SymPy evaluation result with `success: true` and `residual_error` less than or equal to `1e-10`, THE Chat_View SHALL render the Receipt_Badge in the **Verified** state (green indicator, label "CAS Verified").
2. WHEN the Backend returns no SymPy evaluation result for an assistant message, THE Chat_View SHALL render the Receipt_Badge in the **Unverified** state (amber indicator, label "Unverified — LLM heuristic").
3. WHEN the Backend returns a SymPy evaluation result with `success: false` or a timeout signal, THE Chat_View SHALL render the Receipt_Badge in the **Unable_to_Check** state (muted indicator, label "Unable to Check").
4. THE Chat_View SHALL NOT set `verified: true` on any message object unless a corresponding `success: true` SymPy result has been received for that message via SSE.
5. WHEN a message carries the **Unverified** badge, THE Chat_View SHALL display the text "Unverified — LLM heuristic" adjacent to the badge without omitting it.

### Requirement 2: Fix Chat Scroll to Bottom

**User Story:** As a user reading a long derivation streamed token by token, I want the chat to scroll to the bottom as new content arrives, so that I can follow the answer without manually scrolling.

#### Acceptance Criteria

1. WHEN a new assistant message token is appended during streaming, THE Chat_View SHALL scroll the message container to its bottom within one animation frame.
2. WHEN streaming ends and the final message is complete, THE Chat_View SHALL ensure the bottom of the last message is visible in the viewport.
3. WHILE the user has manually scrolled upward more than 80 px from the bottom, THE Chat_View SHALL NOT auto-scroll on new token arrival.
4. WHEN the user sends a new message, THE Chat_View SHALL immediately scroll to the bottom regardless of the current scroll position.

---

### Requirement 3: Strip Raw Model Tokens from Output

**User Story:** As a user reading an AI response, I want the text to be clean prose without internal model tokens, so that raw training artifacts do not appear in my derivation output.

#### Acceptance Criteria

1. WHEN the Backend receives a streaming chunk containing any of the tokens `<answer>`, `</answer>`, `<solution>`, `</solution>`, `<|im_end|>`, `<|im_start|>`, `<|endoftext|>`, or `</sstream>`, THE Backend SHALL strip those tokens before forwarding the chunk to the SSE stream.
2. WHEN a token is stripped, THE Backend SHALL NOT replace it with whitespace or any substitute character — the surrounding text SHALL be concatenated directly.
3. THE Chat_View SHALL apply a secondary client-side strip of the same token list to any chunk received over SSE, so that tokens leaked before the fix are also removed.

### Requirement 4: Update the Model Catalog to the Three Sovereign Models

**User Story:** As a researcher running Vigyan Pro on a mid-range laptop, I want the model catalog to list only the three current Apache 2.0 sovereign models with accurate RAM and size information, so that I can choose the right engine for my hardware.

#### Acceptance Criteria

1. THE CLI SHALL list exactly three models: Daily_Model, Production_Model, and Advanced_Model — with no additional entries.
2. WHEN the user runs `vigyan models`, THE CLI SHALL display for each model: its alias, filename, formatted size (GB), required RAM (GB), and an availability badge that reflects whether the user's system has sufficient free RAM.
3. THE CLI SHALL resolve the aliases `4b`, `gemma4`, `gemma:4b` to the Daily_Model filename `gemma-4-e4b-qat-q4-0.gguf`.
4. THE CLI SHALL resolve the aliases `7b`, `vigyan:7b` to the Production_Model filename `vigyan-7b-quad-master-q4_k_m.gguf`.
5. THE CLI SHALL resolve the aliases `12b`, `gemma:12b`, `gemma4:12b` to the Advanced_Model filename `gemma-4-12b-qat-q4-0.gguf`.
6. WHEN the user runs `vigyan pull 4b` (or any valid alias), THE CLI SHALL download the correct GGUF file from the configured Hugging Face URL to `~/.vigyan/models/`.
7. IF the system's available RAM is less than the model's required RAM, THEN THE CLI SHALL display a RAM advisory before the download begins and proceed only after the user confirms.
8. THE Model_Switcher in the App Titlebar SHALL display segments labeled "4B Daily", "7B Production", and "12B Advanced" corresponding to the three models.

### Requirement 5: Backend Support for Gemma 4 Prompt Format and Context Windows

**User Story:** As a user asking Vigyan Pro long multi-step physics derivations, I want the Gemma 4 models to use their correct chat template and context window, so that answers are not truncated and reasoning chains are coherent.

#### Acceptance Criteria

1. WHEN the Daily_Model or Advanced_Model is loaded, THE Backend SHALL apply the Gemma 4 chat template: `<start_of_turn>user\n{prompt}<end_of_turn>\n<start_of_turn>model\n`.
2. WHEN the Daily_Model is loaded, THE Backend SHALL configure the llama.cpp context window to 131072 tokens (128 K).
3. WHEN the Advanced_Model is loaded, THE Backend SHALL configure the llama.cpp context window to 262144 tokens (256 K).
4. WHEN the Production_Model is loaded, THE Backend SHALL apply the OLMo 2 chat template and configure a context window of 4096 tokens.
5. WHILE any model is active, THE Backend SHALL enforce a RAM governor that refuses to load a model whose required RAM exceeds `available_system_ram_gb × 0.85`, and SHALL return an error response with the message "Insufficient RAM to load this model safely."
6. WHEN the Backend emits the system prompt to any loaded model, THE Backend SHALL use exactly this text: "You are Vigyan, a sovereign offline STEM assistant. Provide exact, step-by-step scientific and mathematical derivations. Never fabricate numerical results. When in doubt, defer to the CAS engine."

### Requirement 6: Wire the Receipt System End-to-End

**User Story:** As an engineer filing a patent, I want every CAS-verified computation in Vigyan Pro to generate a cryptographically signed receipt saved to disk, so that I can prove the derivation was performed offline and reproduce it independently.

#### Acceptance Criteria

1. WHEN the SymPy_Engine evaluates an expression and returns `success: true`, THE Backend SHALL call `generate_derivation_receipt()` from `derivation_receipt.py` with the question text, expression, exact result, LaTeX result, numeric approximation, and the active model name.
2. WHEN a Receipt is generated, THE Backend SHALL save it to `~/.vigyan/receipts/<sha256_prefix>-<timestamp>.rcpt.json` within 500 ms of the SymPy result being available.
3. WHEN a Receipt is saved to disk, THE Backend SHALL emit an SSE event of type `receipt_ready` containing the receipt `id` field, the `exact_analytical` result, and the file path.
4. WHEN the App frontend receives a `receipt_ready` SSE event, THE Chat_View SHALL attach the receipt to the corresponding assistant message and render the Receipt_Badge in the **Verified** state.
5. WHEN the user clicks the Receipt_Badge on a Verified message, THE App SHALL open the Receipt_Inspector panel showing all receipt fields defined in Vigyan Receipt Schema v1.0.
6. FOR ALL valid Receipt files saved to `~/.vigyan/receipts/`, re-running `vigyan verify <file>` SHALL return exit code 0 and print "VERIFIED" to stdout (round-trip property: generate then verify produces consistent hash).
7. WHEN `generate_derivation_receipt()` is called with an expression `E` and result `R`, THE Receipt SHALL contain a `derivation[0].exact_analytical` field equal to the string representation of `R` (invariant: receipt content matches the SymPy output).

### Requirement 7: Receipt Inspector Panel

**User Story:** As a PhD student who needs to cite a computation, I want a side panel that shows the full receipt details — expression, residual, hash, and re-run action — so that I can verify and export the proof without leaving the application.

#### Acceptance Criteria

1. THE App SHALL include a `ReceiptInspector.svelte` component rendered in a 264 px fixed-width right panel.
2. WHEN no receipt is active, THE Receipt_Inspector SHALL display the placeholder text "Select a verified answer to inspect its receipt."
3. WHEN a receipt is active, THE Receipt_Inspector SHALL display: expression, engine version (SymPy), residual error, model name, runtime in seconds, network bytes sent (always 0), and the receipt SHA-256 hash.
4. WHEN the user clicks "Re-run Verification" in the Receipt_Inspector, THE App SHALL invoke `vigyan verify` via the Backend and update the Receipt_Inspector status within 10 seconds.
5. WHEN the user clicks "Copy as LaTeX", THE App SHALL write the LaTeX string from the receipt to the system clipboard.
6. WHEN the user clicks "Export PDF", THE App SHALL save a formatted PDF of the receipt to the user's Downloads folder and display the saved path in a toast notification.
7. WHILE the Receipt_Inspector is open on a widescreen viewport (≥ 1200 px), THE App SHALL display the Session_Rail, Chat_View, and Receipt_Inspector simultaneously without overlapping content.

### Requirement 8: UI Shell Redesign with ExperimentLab Identity

**User Story:** As a user who wants Vigyan Pro to look like a professional STEM instrument rather than a generic AI chatbot, I want a distinctive interface with the ExperimentLab color palette and layout, so that the product has a recognizable identity.

#### Acceptance Criteria

1. THE App SHALL use `#0A0A0B` as the primary background color for all panels (not `#000000` or `#020408`).
2. THE App SHALL use `#FF7B5F` (Coral_Accent) as the primary interactive accent color for send buttons, active badges, and hover states, replacing all prior emerald (`#10b981`) and sky-blue (`#38bdf8`) accents in interactive controls.
3. THE App's global font stack SHALL be `system-ui, -apple-system, "Segoe UI", sans-serif` with no external font imports or CDN font requests.
4. THE Titlebar SHALL be exactly 36 px tall and SHALL contain, left-to-right: traffic-light circles (macOS-style), app title "Vigyan Pro", the Model_Switcher nav, the engine status indicator, and action buttons (New, Models, Settings).
5. THE App layout SHALL use a 3-column CSS grid: 220 px Session_Rail | flex Chat_View | 264 px Receipt_Inspector, within a 36 px Titlebar row.
6. WHEN the user hovers over a session item in the Session_Rail, THE Session_Rail SHALL show a background highlight transition completing within 130 ms.
7. THE App SHALL respect the `prefers-reduced-motion` media query: WHEN it is set to `reduce`, THE App SHALL suppress all CSS animations and transitions except opacity changes.
8. THE App's empty-state screen SHALL display the headline "What are we working on?" and four suggested prompt chips for STEM topics without any ExperimentLab or third-party logo that the user has not approved.
9. WHEN a new chat screen appears after a navigation event, THE Chat_View SHALL animate in with a `translateY(6px) → none` fade-up over 240 ms (suppressed when `prefers-reduced-motion: reduce`).
10. THE App SHALL display the ExperimentLab wordmark in the Titlebar using the application's own SVG assets from `assets/icons/` and SHALL NOT use the Anthropic, Apple, or any third-party logo styling.

### Requirement 9: Command Palette

**User Story:** As a power user, I want a keyboard-driven command palette to navigate sessions, toggle themes, and trigger receipt actions without using the mouse, so that I can work efficiently during long derivation sessions.

#### Acceptance Criteria

1. WHEN the user presses ⌘K (macOS) or Ctrl+K (Windows/Linux), THE App SHALL open the Command_Palette modal overlay.
2. WHEN the Command_Palette is open, THE App SHALL display a text input and a list of commands including at minimum: "New session", "Open receipts", "Toggle theme", "Re-run verification", "Export receipt as PDF", and "Settings".
3. WHEN the user types in the Command_Palette input, THE App SHALL filter the command list to entries whose labels contain the typed substring (case-insensitive), within one keypress event.
4. WHEN the user presses Escape while the Command_Palette is open, THE App SHALL close it without executing any command.
5. WHEN the user selects a command by pressing Enter or clicking its row, THE App SHALL execute that command and close the Command_Palette.
6. WHEN the Command_Palette opens, THE App SHALL focus the text input automatically so the user can type immediately.

### Requirement 10: `vigyan verify` CLI Command

**User Story:** As a researcher who received a `.rcpt.json` file from a colleague, I want to run `vigyan verify` to re-execute the derivation locally and confirm the hash, so that I can independently validate the computation without installing any cloud software.

#### Acceptance Criteria

1. WHEN the user runs `vigyan verify <filepath>`, THE CLI SHALL load the JSON from `<filepath>`, call `verify_derivation_receipt()`, and print the ASCII audit report produced by `format_cli_receipt_report()`.
2. WHEN verification passes, THE CLI SHALL exit with code 0 and print "VERIFIED" on the final output line.
3. WHEN verification fails due to a hash mismatch, THE CLI SHALL exit with code 1 and print the reason including the expected and computed hash values.
4. WHEN verification fails due to a SymPy divergence in a derivation step, THE CLI SHALL exit with code 1 and identify the 0-indexed step number (where step 0 is the first derivation step) and the computed versus expected values.
5. IF the file at `<filepath>` does not exist, THEN THE CLI SHALL exit with code 2 and print "Error: file not found: <filepath>".
6. IF the file at `<filepath>` is not valid JSON, THEN THE CLI SHALL exit with code 2 and print "Error: invalid JSON in receipt file".
7. WHEN verification completes, THE CLI SHALL report total wall-clock time in milliseconds for the re-evaluation.

### Requirement 11: `vigyan receipts` CLI Command

**User Story:** As a user who runs Vigyan Pro regularly, I want to list all saved receipts from the terminal, so that I can find and re-verify past computations without opening the GUI.

#### Acceptance Criteria

1. WHEN the user runs `vigyan receipts`, THE CLI SHALL scan `~/.vigyan/receipts/` and print a table with columns: filename, created timestamp, question (truncated to 60 characters), and verification status.
2. WHEN `~/.vigyan/receipts/` contains no receipt files, THE CLI SHALL print "No receipts found in ~/.vigyan/receipts/" and exit with code 0.
3. WHEN the user runs `vigyan receipts --verify-all`, THE CLI SHALL run `verify_derivation_receipt()` on each file and append a pass/fail indicator to each row.
4. WHEN the user runs `vigyan receipts --export <dir>`, THE CLI SHALL copy all receipt files to `<dir>`, creating the directory if it does not exist, and print the count of files exported.
5. THE CLI SHALL sort receipt rows by created timestamp descending (newest first) by default.

### Requirement 12: Non-Commercial Licence Declaration

**User Story:** As a commercial organisation evaluating Vigyan Pro, I want the application to clearly state the Free Tier licence terms at first run and in the about screen, so that I know I need a commercial seat before deploying it in a business context.

#### Acceptance Criteria

1. THE App SHALL include a `LICENCE-FREE-TIER.md` file at the repository root containing the terms: free for personal, academic, and non-commercial research use; commercial use requires a paid seat; no warranty.
2. WHEN the App is launched for the first time (no prior `~/.vigyan/config.json`), THE App SHALL display the licence summary in a modal overlay with an "I Understand" button before showing the main interface.
3. WHEN the user clicks "I Understand", THE App SHALL write `{"licence_accepted": true, "accepted_at": "<ISO8601 timestamp>"}` to `~/.vigyan/config.json` and not show the modal again.
4. THE App Settings panel SHALL include a "Licence" section showing the tier name ("Personal — Free"), the acceptance date, and a link to `LICENCE-FREE-TIER.md`.
5. WHEN the user runs `vigyan --version`, THE CLI SHALL print the version string followed by "Licence: Non-Commercial Free Tier".
6. THE App and CLI SHALL NOT require a licence key, account creation, or network request to validate the Free Tier licence.

### Requirement 13: Windows Installation Without Pre-installed Python

**User Story:** As a Windows user who does not have Python installed, I want to install and launch Vigyan Pro without manually setting up a Python environment, so that the setup friction is no higher than installing a typical desktop app.

#### Acceptance Criteria

1. THE Windows installer package SHALL bundle a Python 3.12 embedded distribution inside the application directory so that no system-level Python installation is required.
2. WHEN the user launches `Vigyan-Pro.bat` on a Windows machine without Python in `PATH`, THE launcher SHALL detect the bundled Python and use it to start the Backend without displaying a Python error.
3. WHEN the bundled Python is used, THE installer SHALL pre-install the required packages (`llama-cpp-python`, `sympy`, `pint`, `flask`, `flask-cors`) into the bundled environment during installation, not at first run.
4. IF the bundled Python environment is missing or corrupted, THEN THE launcher SHALL display the message: "Vigyan Pro setup is incomplete. Please re-run the installer." and exit cleanly.
5. THE installer SHALL complete the full installation in under 3 minutes on a standard broadband connection (excluding model download time).
